# Ветки, pull request и закрытие задач

Документ описывает, как в BYDLO связаны задачи, ветки и pull request, и когда задача закрывается
автоматически. Правила одинаковы для GitHub и для зеркала на Gitea, но автоматизация реализована
только в GitHub Actions.

## Ветки

| Ветка | Назначение |
|---|---|
| `main` | Ветка по умолчанию. Отсюда собираются релизы, здесь лежат workflow, которые работают с повышенными правами. |
| `developer` | Интеграционная ветка. Сюда идут все обычные pull request. |
| `<тема>/<номер>-<описание>` | Рабочая ветка одной задачи. Имя описывает задачу; `codex` в имени не используется. |

Путь задачи: issue → рабочая ветка → pull request в `developer` → merge → релизный pull request
`developer` → `main`. Релизный pull request — единственный, который нацелен на `main`.

## Закрывающие ссылки

Задача связывается с pull request через ключевое слово и ссылку в **теле** pull request:

```
Closes #449
Fixes #449
Resolves #449
Closes endercodezz/BYDLO#449
```

Поддерживаются формы `Closes` / `Close` / `Closed`, `Fixes` / `Fix` / `Fixed`,
`Resolves` / `Resolve` / `Resolved` в любом регистре, с двоеточием и без. Несколько ссылок в одном
теле допустимы, повторы схлопываются.

Не считаются закрывающими ссылками:

- упоминание без ключевого слова (`#449` само по себе);
- ключевое слово, приклеенное к другому слову (`prefix #449`);
- ссылка на чужой репозиторий (`other/repo#449`);
- ссылка внутри блока кода, строчного кода или цитаты — примеры в описании ничего не закрывают;
- ссылка на pull request: номер разбирается, но при проверке через API pull request пропускается.

## Когда задача закрывается

| Момент | Кто закрывает |
|---|---|
| Создание, редактирование или переоткрытие pull request с базой ровно `developer` | `close-linked-issues.yml` |
| Merge pull request в `developer` или в `main` | `post-merge-cleanup.yml` |

Раннее закрытие нужно потому, что GitHub применяет ключевые слова только при merge в ветку по
умолчанию, а auto-merge вливает как `github-actions[bot]` и ключевые слова пропускает вовсе.

## Семантика и границы

- База проверяется дважды: в условии события и повторным запросом актуального состояния pull request.
  Устаревшее или переигранное событие ничего не закроет.
- Закрывает только текущий автор pull request и только при правах `write`, `maintain` или `admin`
  в целевом репозитории. `author_association` из события для этого недостаточно.
- Уже закрытые задачи пропускаются. Pull request как ресурс не закрывается никогда.
- Задача не переоткрывается: если pull request закрыли или перенацелили мимо `developer`, решение
  сопровождающего остаётся в силе.
- Каждое закрытие сопровождается комментарием на русском со ссылкой на pull request.
- Повторные и конкурентные события не ломают работу: все шаги идемпотентны, группы `concurrency` нет,
  иначе GitHub молча отбрасывал бы поставленные в очередь запуски.

## Безопасность

Workflow работает по `pull_request_target` с правом `issues: write`, поэтому:

- файл workflow всегда берётся из ветки по умолчанию, форк не может его подменить;
- checkout и запуск кода pull request запрещены — в job нет ни одного `uses:`;
- в скрипт не подставляются заголовок, тело и имя ветки pull request: читаются только
  структурированные поля GitHub;
- парсер `.github/scripts/closing-references.sh` загружается через API из коммита ветки по умолчанию,
  а не из базового ref pull request;
- права ограничены `contents: read`, `issues: write`, `pull-requests: read`.

## Активация

`close-linked-issues.yml` начинает работать только после попадания в `main`: `pull_request_target`
запускает файл из ветки по умолчанию. Одного pull request в `developer` недостаточно.

## Проверка

- `bash .github/scripts/test-closing-references.sh` — грамматика парсера на фикстурах, без сети и API.
- `scripts/check.sh` запускает этот тест вместе с остальными изолированными проверками.
- `tests/Bydlo.Tests/CloseLinkedIssuesWorkflowTests.cs` — статические проверки workflow: триггер,
  точная база, минимальные права, отсутствие checkout, отсутствие подстановки текста pull request.
