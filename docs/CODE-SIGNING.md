# Подпись кода для Windows

Связано: #215 (установщик), #216 (проверка подписи при автообновлении), #246 (UAC).

## Проблема

Windows показывает BYDLO как приложение «неизвестного издателя»: SmartScreen предупреждает
при запуске, UAC-запрос выглядит подозрительно (особенно вместе с #246).

## Выбранный вариант

**Azure Trusted Signing** — основной вариант:

- недорогая подписка, проверка личности/организации один раз;
- подпись выполняется из CI релиза через OIDC (федеративные credentials GitHub Actions),
  файл `.pfx` и приватный ключ нигде не хранятся;
- встроенная метка времени RFC 3161, отдельный timestamp-сервер не нужен;
- покрывает `BYDLO.exe`, `helper/Bydlo.Helper.exe` и будущий установщик (#215).

Запасной вариант — **SignPath Foundation** (бесплатно для open-source из публичного
репозитория, но с внешней очередью и политикой фонда). Классический OV/EV-сертификат
на токене — дорого и неудобно для CI. Самоподписанный сертификат не убирает
предупреждения SmartScreen и не используется.

## Что подписывается

- `publish/BYDLO-win-x64/BYDLO.exe` и `publish/BYDLO-win-x64/helper/Bydlo.Helper.exe`;
- `publish/BYDLO-win-arm64/BYDLO.exe` и `publish/BYDLO-win-arm64/helper/Bydlo.Helper.exe`;
- будущий установщик из #215 — тем же сертификатом и с той же меткой времени.

Подпись выполняется после `desktop`/`windows-parity` и до упаковки `package`, чтобы
`SHA256SUMS.txt` считался уже по подписанным файлам.

## Секреты

Только секреты CI (Settings → Secrets and variables → Actions), никогда в репозитории:

- `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_SUBSCRIPTION_ID`;
- `AZURE_TRUSTED_SIGNING_ACCOUNT`, `AZURE_TRUSTED_SIGNING_PROFILE`;
- `BYDLO_UPDATE_SIGNING_KEY` — PEM-ключ P-256 для каталога обновлений (см. ниже);
- проверку `git grep -ri 'pfx\|p12\|BEGIN PRIVATE'` репозиторий проходит пустым.

Файлов `.pfx`/`.p12`/`.snk` в репозитории нет и быть не должно.

## Проверка релиза

Для тегов `v0.3.1`, `v0.4.0`, `v0.4.1`, `v0.4.2` и `v0.4.3` CI пропускает задание подписания.
В `v0.4.3` BYDLO, помощник и установщики Windows/macOS поставляются без подписи
сертификатом издателя; notarization macOS также пропускается. CI сохраняет проверки
комплектности, SHA-256 и GitHub attestations. Для будущих тегов подпись обязательна.

Репетиция упаковки без подписи: ручной запуск `CI` с `skip_signing=true`.
Он не создаёт тег или черновик релиза. Постоянная подпись отслеживается в #392.

Обязательный шаг релиза (job `sign-windows` в `.github/workflows/ci.yml`):

1. `Azure/trusted-signing-action` подписывает оба `BYDLO.exe` и оба `helper/Bydlo.Helper.exe`;
2. `signtool verify /pa /v` подтверждает подпись каждого файла, неуспех роняет job;
3. `package` проверяет engine-bundle и только потом считает `SHA256SUMS.txt`.

Локально без секретов подпись не ставится. За пределами явных исключений CI без
настроенных credentials останавливает выпуск. Проверка происхождения через attestations
не заменяет системную подпись Windows/macOS.

## Миграция Azure/login v3.1.0 (#428)

В `native-packages` закреплён commit `a641126d1b8aa4d1fa005f4f92df94a3a4c4c906`
релиза [v3.1.0](https://github.com/Azure/login/releases/tag/v3.1.0), а не SHA объекта
аннотированного тега. Главная несовместимость v3 — переход с Node.js 20 на 24.
Задание использует GitHub-hosted `windows-latest`, как и уже обновлённые checkout/setup-dotnet;
для собственного runner нужна поддержка Node.js 24. Azure CLI для OIDC должен быть не ниже 2.30.

Проверены release notes v3.0.0–v3.1.0 и `action.yml`: прежние `client-id`, `tenant-id`,
`subscription-id` совместимы. Используются только secrets, OIDC и Azure Public Cloud
(стандартные `environment=azurecloud`, `audience=api://AzureADTokenExchange`,
`auth-type=SERVICE_PRINCIPAL`). Вход по паролю и дополнительная Az PowerShell-сессия
не включаются. Маскирование client ID и завершающая очистка контекста остаются включёнными
по умолчанию; их отключающие параметры не задаются.

Модель доверия не меняется: `contents: read` и `id-token: write` ограничены заданием;
оно доступно только для тега релиза или ручного запуска, не для PR. Вход Azure дополнительно
ограничен Windows, наличием client ID и обязательной подписью. Федеративные credentials
должны доверять только разрешённым ref/окружениям, но не `pull_request`.

Изолированные тесты проверяют YAML, закрепление версии, inputs, permissions и условия
запуска. Они не выполняют вход Azure. Сопровождающий должен отдельно выполнить разрешённый
подписывающий прогон с настроенными credentials (#392), проверить OIDC, подпись пакетов
и post-cleanup. Успешная реальная подпись этой миграцией не подтверждается.

## Подписанный каталог обновлений (#411)

### Модель угроз

До #411 `PackagedAppUpdater` передавал `GithubSource` прямо в Velopack `UpdateManager`.
Размер и SHA-256 брались из того же feed, который контролирует атакующий, поэтому
одновременная подмена пакета и метаданных проходила проверку: хеш из подделанного feed
совпадал с подделанным пакетом. Отдельно опасен Windows: Velopack 1.2.161 может распаковать
и заменить `Update.exe` уже внутри `DownloadUpdatesAsync`, поэтому проверка «после скачивания»
защищает слишком поздно.

Модель угроз: компрометация аккаунта/релиза на хостинге, подмена ответа GitHub, подмена
файлов в кэше обновлений, откат на старую уязвимую версию. Не покрывается: компрометация
машины разработчика или CI с доступом к приватному ключу, а также подмена самого
установленного BYDLO.

### Корень доверия

- Один файл `releases-catalog.json` публикуется как asset релиза вместе с пакетами.
  Формат: `{ "payload": "<base64 UTF-8 JSON>", "keyId": "...", "signature": "<base64>" }`.
- `payload` — канонические UTF-8 байты, на которых считается подпись: `schemaVersion`,
  `issuedAt`, `expiresAt`, `channel`, `version` и массив `packages` с `rid`, `fileName`,
  `size`, `sha256` для каждого RID.
- Алгоритм: ECDSA P-256 / SHA-256, только `System.Security.Cryptography`. Новых пакетов нет,
  собственных примитивов нет.
- Публичные ключи зашиты в приложение (`Bydlo.Core.Updates.UpdateTrustRoots`): карта
  `keyId → SPKI base64`, слот текущего ключа, слот следующего ключа для ротации и список
  отозванных `keyId`. **Публичный ключ никогда не берётся из feed.** Пока в
  `CurrentPublicKeySpki` стоит заглушка, любой каталог отклоняется: обновления не ставятся,
  рабочая версия сохраняется.
- Ключ выпускается локально: `scripts/new-update-signing-key.ps1` печатает SPKI base64 и
  `keyId`, приватный ключ пишет только вне репозитория. Приватный ключ хранится
  исключительно в секрете `BYDLO_UPDATE_SIGNING_KEY`.

### Что аутентифицируется

Подпись покрывает версию, канал, RID, имя пакета, размер и обязательный SHA-256. Дополнительно
клиент проверяет, что `fileName` равен `BydloDesktop-<version>-<rid>-full.nupkg`, что RID
входит в поддерживаемый список, а канал — `stable`. Velopack получает только те данные,
которые совпали с подписанной записью: сравнение выполняется **до** `DownloadUpdatesAsync`
и повторно перед применением. Любое расхождение закрывает установку.

Версия внутри пакета сверяется при выпуске: `scripts/sign-update-catalog.ps1` читает
`<version>` из nuspec каждого финального пакета и отказывается подписывать каталог, если она
не совпадает с версией каталога. Так подписанная версия не может разойтись с содержимым пакета.

### Ротация и отзыв

1. Выпустить новую пару `scripts/new-update-signing-key.ps1 -KeyId bydlo-update-YYYY-NN`
   (PowerShell 7, вне репозитория).
2. Вписать новый `keyId` и SPKI в слот `UpdateTrustRoots.Next*` и выпустить релиз: клиенты этой
   версии уже доверяют обоим ключам, а каталог по-прежнему подписан старым.
3. Когда обновилось большинство установок, перенести новый ключ в слот `Current*`; при
   необходимости добавить прежний `keyId` в `RevokedKeyIds`.
4. После мержа и до тега заменить секрет `BYDLO_UPDATE_SIGNING_KEY` новым приватным ключом.

`sign-update-catalog.ps1` подписывает каталог как `CurrentKeyId` и отказывается работать, если
публичная часть секрета не совпадает с `CurrentPublicKeySpki`. Поэтому забытая замена секрета
останавливает релиз, а не выпускает каталог, который клиенты отклонят. Пошаговая процедура для
агентов — навык `.claude/skills/update-key-rotation`.

Отзыв действует немедленно: каталог с отозванным `keyId` отклоняется, даже если подпись
формально верна. Компрометация ключа без отзыва в установленных копиях не лечится —
это известное ограничение схемы без онлайн-статуса.

### Downgrade, replay, срок действия и часы

- Версия каталога должна быть строго новее установленной; равная и старая отклоняются.
  Это же защищает от повторного проигрывания ранее подписанного каталога.
- `expiresAt` проверяется по системным часам с допуском 10 минут; просроченный каталог
  отклоняется (fail closed). `issuedAt` в будущем за пределами того же допуска тоже
  отклоняется — так ошибка часов не превращается в приём произвольных метаданных.
- Каталог подписывается на 365 дней. Если за год не вышло ни одного релиза, автообновление
  останавливается до следующего релиза (или повторной подписи каталога текущей версии);
  ручное обновление по-прежнему доступно.
- Разрешённый recovery rollback (#412) — отдельный сценарий с собственным доверенным
  источником. Обычное обновление откат не выполняет; в коде для #412 оставлен только
  явный флаг-хук, поведение не реализовано.

### Скачивание и применение

- Каталог скачивается с ограничением 64 КиБ, таймаутом 20 с и отменой; тело читается
  не более чем на байт сверх лимита.
- Каталог не пишется на диск: он разбирается в памяти, поэтому права на кэш, символические
  ссылки и неполные staging-файлы к нему не применимы. Кэш пакетов остаётся за Velopack,
  а его содержимое перекрывается повторной сверкой перед применением.
- Пакет скачивает Velopack, но только после сверки с подписанной записью; перед применением
  запись сверяется повторно, поэтому подмена файла между проверкой и применением закрывает
  установку.
- Несовпадение, отсутствие подписи, неизвестный или отозванный ключ, неподдерживаемый
  RID/канал и просроченные метаданные оставляют рабочую версию и показывают локализованное
  сообщение (en + ru).

### CI

`package` собирает финальные пакеты, проверяет `SHA256SUMS.txt`, затем
`scripts/sign-update-catalog.ps1` строит payload по этим же файлам и подписывает его ключом
из `BYDLO_UPDATE_SIGNING_KEY`. Без секрета шаг падает: неподписанный каталог не публикуется.
`stage-release.ps1 -VerifyOnly` требует каталог и сверяет его с пакетами, поэтому feed
становится видимым только вместе с корректным каталогом.

### Границы гарантий

Каталог подтверждает, что метаданные и SHA-256 выпущены владельцем ключа. Он не заменяет
подпись Windows/macOS: Authenticode, Developer ID и notarization отслеживаются в #392 и здесь
не обещаются. Проверка подписи macOS bundle upstream (velopack#975) тоже не входит в эту
задачу. Attestations происхождения (#216) полезны, но клиент их не проверяет и не считает
доказательством подлинности.
